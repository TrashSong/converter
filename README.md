# 1. Тема лабораторної роботи та її опис

Тема: "Система контролю версій Git та співпраця через GitHub"

Загальний опис теми
Git — це розподілена система контролю версій (VCS, Version Control System), створена Лінусом Торвальдсом у 2005 році для розробки ядра Linux. Сьогодні Git є де-факто стандартом для контролю версій у програмному забезпеченні та використовується мільйонами розробників по всьому світу.

Система контролю версій дозволяє відстежувати зміни в коді з часом, повертатися до попередніх версій, працювати над проектом командою без конфліктів, експериментувати з новими функціями в ізольованих гілках, та багато іншого. Git зберігає повну історію проекту, що дозволяє відповісти на питання "хто, що, коли і чому змінив" у будь-який момент часу.

Розуміння Git є критично важливим для сучасних розробників, незалежно від спеціалізації. Це не просто інструмент для збереження коду — це фундамент для ефективної командної роботи, continuous integration/deployment, code review процесів та професійної розробки ПЗ.

# 2. Мета заняття

Що ви навчитеся робити:

Розуміти основні концепції систем контролю версій
Створювати та керувати Git репозиторіями
Фіксувати зміни (commits) та працювати з історією
Створювати та об'єднувати гілки (branches)
Працювати з віддаленими репозиторіями (GitHub, GitLab)
Співпрацювати з іншими розробниками через pull requests
Вирішувати конфлікти злиття
Використовувати SSH-ключі та токени безпечно
Працювати з .gitignore та захищати конфіденційні дані

Навички для майбутньої кар'єри:

Версіонування коду в командній розробці
Code review та collaboration workflows
CI/CD integration
Open source contribution
Portfolio management через GitHub

# 3. Відповіді на контрольні запитання

1. Git — це інструмент: розподілена система контролю версій, яка встановлюється на комп'ютер. Це програмне забезпечення, яке відстежує зміни у файлах.
   GitHub — це сервіс: веб-платформа, яка використовує Git. Вона надає хмарне сховище для ваших репозиторіїв, а також додаткові функції: Pull Requests, Issues, code review, CI/CD та зручний веб-інтерфейс.
2. Це означає, що кожен розробник, який клонує репозиторій, отримує повну копію всієї історії проєкту.
3. git init — Ініціалізує новий, порожній Git-репозиторій у поточній папці.
   git clone [url] — Клонує вже існуючий віддалений репозиторій на локальний комп'ютер. Ця команда автоматично створює папку з проєктом і підключає віддалений репозиторій.
4. Staging Area — це проміжний етап між робочими файлами (Working Directory) та вашою історією комітів (Repository). Це дозволяє формувати коміт частинами. Можна змінити 10 файлів, але додати в Staging Area (і потім в коміт) лише 5 з них, які стосуються однієї логічної зміни.
5. git add . — додає до Staging Area всі нові, змінені та видалені файли в поточній папці та всіх її підпапках.
   git add -A — робить те саме, але для всього репозиторію.
6. Conventional Commits — стандарт для повідомлень:
   <type>[optional scope]: <description>
   [optional body]
   [optional footer(s)]
7. git commit --amend
8. Гілка (branch) — це рухомий вказівник на певний коміт.
9. git merge - бере дві гілки і створює новий, спеціальний "merge-коміт", який має двох "батьків" (останні коміти обох гілок).
   git rebase - бере всі коміти з гілки, тимчасово їх "відкладає", переходить на вказану гілку, а потім повторно застосовує ваші коміти один за одним поверх неї.
10. Він відбувається, коли гілка, в яку йде merge, не має нових комітів з того моменту, як була створена нова гілка.
11. Конфлікт виникає, коли Git намагається автоматично об'єднати зміни, але виявляє, що ті самі рядки в тому самому файлі були змінені по-різному в обох гілках. Git не знає, яку версію обрати, і просить вас вирішити це вручну.
12. git rebase переписує історію, створюючи нові коміти з новими хешами.
13. origin — це стандартне ім'я, яке Git дає віддаленому репозиторію, з якого ви склонували проєкт.
14. git fetch тільки завантажує нові дані (коміти, гілки) з віддаленого репозиторію, але не змінює локальні гілки і робочу папку.
    git pull - це дві команди в одній: git fetch + git merge. Вона завантажує нові дані І негайно намагається злити їх у поточну локальну гілку.
15. git push --force примусово перезаписує віддалену гілку локальною версією. Він ігнорує будь-які нові коміти, які могли з'явитися на віддаленій гілці, поки ви працювали локально.
16. git push origin --delete <назва-гілки>
17. --soft:
    Staging Area: Не чіпає.
    Working Directory: Не чіпає.
    --mixed (це режим за замовчуванням):
    Staging Area: Очищується. (Зміни зі "скасованих" комітів переносяться у Working Directory як "неіндексовані").
    Working Directory: Не чіпає.
    --hard:
    Staging Area: Очищується.
    Working Directory: Перезаписується. (Всі не закомічені зміни, а також зміни зі "скасованих" комітів видаляються безповоротно).
18. git reset - переписує історію, "скасовує" коміти, видаляючи їх з історії гілки (переміщуючи HEAD назад).
    git revert - не переписує історію, "скасовує" коміт, створюючи новий коміт, який робить зворотні зміни.
19. git restore --staged <назва-файлу>
20. git restore <назва-файлу>
21. Секрети: Паролі, API-ключі, токени.
    Залежності: Папки типу node_modules/, vendor/.
    Файли ОС: .DS_Store (macOS), Thumbs.db (Windows).
    Файли IDE: .vscode/, .idea/.
    Артефакти збірки: dist/, build/, .exe, .jar.
    Логи: .log.
22. Змінити пароль, видалити його коміт та його історію.
23. SSH
24. Personal Access Token (PAT) — це довгий, випадково згенерований рядок, який використовується замість пароля для аутентифікації в Git-операціях через HTTPS.
25. Pull Request (PR) — це запит на "прийняття ваших змін". Це механізм GitHub, який дозволяє повідомити інших, що ви завершили роботу над гілкою і готові злити її в основну гілку. Команда може переглянути код, обговорити зміни.
26. Issues - це про обговорення.
    Pull Requests (Запити на злиття): Це про код.
27. Fork (Форк) — це особиста копія чужого репозиторію, яка зберігається у вашому власному GitHub-акаунті. Він є основою для Open Source внесків.
28. GitHub Actions — це вбудована в GitHub платформа для CI/CD (Continuous Integration / Continuous Deployment) та автоматизації робочих процесів.
29. Часто. Один коміт = одна логічна зміна.
30. Якомога менше. В ідеалі — від кількох годин до кількох днів. Максимум — тиждень.
31. GitHub Flow, Git Flow, Trunk-Based Development.
32. Ні, в цьому немає сенсу, оскільки всі файли встановлюються тільки локально через package.json та package-lock.json.
